# 任务 1 学习笔记 —— 静态页面原型（前端）

> 对应规范：`docs/v3/03` 任务卡 1；学习清单 `docs/v3/05` 的「任务 1」条目。
> 本轮全部改动在 `frontend/src/`，纯前端 + 内存 mock，无后端、无登录。

## 一、05 清单逐条解释（在本项目中的具体落点）

### 1. 响应式布局

**是什么**：同一套页面在窄屏（手机）和宽屏（桌面）都能正常阅读，靠的是流式布局 + `flex-wrap` + 相对单位（rem），而不是写死像素。

**在哪体现**：
- `src/assets/main.css`：全局容器限宽居中、原子类（`.card` `.btn` `.chip` `.badge`）都用 rem 和 flex；
- `src/components/FilterBar.vue` 的 `.filter-bar__row { display: flex; flex-wrap: wrap; }`：筛选项多时自动换行；
- 各页面（如 `PostView.vue` 的 `.create__row`）学校/专业两个下拉在窄屏靠换行堆叠。

**一句话理解**：不针对具体屏幕写死布局，让内容自己"流"。

### 2. 组件拆分

**是什么**：把页面切成"可复用、职责单一"的块。拆分的信号是：同一段 UI 出现两次，或一块 UI 有自己完整的输入/输出契约。

**在哪体现**：
- `AuthorDisplay.vue`：**身份展示的唯一出口**——匿名渲染纯文本"匿名"（不可点），公开渲染 `RouterLink` 进主页。首页卡片、详情页、回复列表全部复用它，匿名规则改一处生效全局；
- `PostCard.vue`：帖子卡片（徽章 + 作者 + 摘要 + 统计）；
- `ReplyItem.vue`：一条回复 + 楼主"标记有帮助"按钮；
- `FilterBar.vue`：筛选 UI，只负责改 Pinia store 并 emit `change`。

**面试讲法**：我按"身份出口唯一"的原则拆组件，匿名安全不依赖每个页面自觉，而是被 `AuthorDisplay` 这一个组件收口。

### 3. 列表渲染

**是什么**：`v-for` + `:key` 渲染集合并让 Vue 高效复用 DOM。

**在哪体现**：`HomeView.vue` 的 `<PostCard v-for="p in feed" :key="p.id">`；`ProfileView.vue` 的帖子/回复两个 tab；`MeView.vue` 三个 tab。key 用业务 id 而不是数组下标，删除/排序时才不会错位。

### 4. 筛选状态放 URL 还是 Pinia

**是什么**：这是本轮最重要的设计取舍。Pinia 管"运行时的当前筛选"，URL query 管"可分享、可前进后退的筛选"。

**在哪体现**：
- `src/stores/feedFilters.ts`：Pinia store 保存 school/major/intent/tags，并提供 `current()`（转成 mock API 的参数）、`patch()`、`restoreFromQuery()`、`hasAny()`；
- `src/views/HomeView.vue`：筛选变更 → `router.replace` 写入 `?intent=ADVICE&tags=t_study`；页面挂载和 `route.query` 变化时 `restoreFromQuery()`。

**为什么两边都要**：只放 Pinia，刷新/分享链接就丢状态；只放 URL，每次变更都要走路由解析、组件间共享别扭。URL 是"真相来源"（可分享、可前进后退），Pinia 是"工作副本"。浏览器实测：直接访问 `/?school=s_whu&intent=VENT` 能恢复下拉框与选中态，且"已获得帮助"分组计数也跟着筛选变化。

### 5. 为什么"待回答"排序最终由后端决定

**是什么**：前端展示的排序/分组（未回答优先、RESOLVED 不进默认流）只是展示结果；**规则本身必须在服务端实现**，前端不参与判定。

**在哪体现**：`src/mock/api.ts` 的 `feedStatusOf()`（有帮助回复或已关闭 → RESOLVED）、`fetchFeed()`（排除 RESOLVED，UNANSWERED 在前、同组按发布时间早到晚）。任务 3 会把这两个函数原样翻译成 Service 层逻辑 + SQL。

**面试讲法**：排序和可见性规则如果放前端，任何人都能绕过（直接改 JS）。mock 层我刻意把规则写进"假服务端"（api.ts），页面组件只消费结果——这就是任务 3 后端接管的接缝。

## 二、本轮补充理解（05 清单没有、但代码里有的关键点）

1. **匿名是"数据出口规则"不是"隐藏"**：`mock/db.ts` 里每条记录带 `authorId` + `identityMode`（模拟数据库），但 `toAuthorVO()` 是所有 VO 的唯一身份出口，ANONYMOUS 只产出 `{mode:'anonymous'}`；`Post` 类型里根本没有 authorId/schoolId 字段（本轮验收自检时进一步把 schoolId/majorId 从公开 `Post` VO 里删掉了，筛选只发生在"服务端"记录上）。
2. **楼主操作在"服务端"校验**：`toggleHelpful()`/`setCommentsClosed()` 在 mock api 里核对 `record.authorId === currentUserId`，`PostDetail.isAuthorOfPost` 由服务端算好下发，前端 VO 里没有 authorId 可供伪造。
3. **公开主页强制过滤**：`fetchProfile()` 的查询条件模拟 `WHERE identity_mode='PUBLIC' AND deleted_at IS NULL`，匿名历史无法从主页反推。
4. **mock 数据在内存里，刷新即重置**——这是静态原型阶段的已知限制（浏览器实测时新建的帖子刷新后消失）。任务 3 接真实后端后消失。

## 四、本轮开发过程中的问题与解答

本模块开发期间（含验收反馈）开发者提出的问题：

1. **"发帖页'以什么身份发布'两个选项没对齐"** —— 判断正确。根因：`PostView.vue` 样式 `.create__group input` 本意是美化文本框，却把 `width:100%`、边框、内边距也套在了 `type="radio"` 上，单选框被撑满整行导致错位。修复：选择器改为 `.create__group input:not([type="radio"])`。教训：表单样式要按输入类型收窄选择器，`input` 一把梭必误伤 radio/checkbox。
2. **"首页卡片想点任意处进详情，而不是只有标题"** —— 需求合理。方案用 stretched-link：标题 `<a>` 加 `::after { position:absolute; inset:0 }` 铺满整卡（卡片 `position:relative`），整卡即点击区；作者昵称 `.author-link` 用 `z-index:1` 抬到覆盖层之上，进主页仍可单独点击，且 HTML 里不出现嵌套 `<a>`。浏览器实测：点正文空白→进帖子，点昵称→进 `/u/annagrad`。
3. **"修完整卡可点后，顶部导航'发帖/我的'点不开了"** —— 真 bug，是我引入的。根因：sticky 导航没有 `z-index`，卡片覆盖层在文档流后面、同层级时绘制在导航之上；页面一滚动，卡片滑到导航下方，覆盖层就把导航链接"扣"住了（用 `elementFromPoint` 实测：导航链接位置的最上层元素是卡片的隐形 `<a>`）。修复：`.app-header` 加 `z-index:10`。教训：**stretched-link/透明覆盖层必须和所有 sticky/fixed 层做层级对账**；排查这类"点不动"问题先看 DevTools 的 Computed→点击位置，或直接 `document.elementFromPoint()` 看真实命中元素。
4. **"我的页面还是打不开 + 卡片现在全都点不开"** —— 排查结论：磁盘上的代码经全新加载实测正常（真实点击"我的"→ /me；点卡片正文 → /posts/p1）。旧页签里点不动的原因是 vite dev 的已知坑：路由组件是懒加载 chunk，文件被多轮热更后，**旧页签**里已加载的模块再去动态 import 会失败，vue-router 导航静默中止，表现为"点什么都没反应"（DevTools Console 有 `Failed to fetch dynamically imported module`）。修复：`router.onError` 捕获该错误后自动整页刷新一次（5 秒防抖，避免模块真缺失时死循环）——这也是生产发版后旧标签页访问新 hash chunk 的标准兜底。开发者侧动作：遇到"点不开"先 Ctrl+Shift+R 硬刷新一次再报现象。
5. **"卡片底部标签间距太大"** —— 根因：`.post-card__foot` 用 `justify-content: space-between`，标签和统计被均匀拉开。修复：标签包进 `.post-card__tags`（flex + gap 0.6rem）靠左成组，统计仍靠右。教训：space-between 只适合"两端"布局，中间元素多了会变成"撒胡椒面"。

**流程教训（开发者明确批评过"修一个 bug 出一个新 bug"）**：每轮修复后不能只测被改的那一点，必须回归：①顶部导航三个入口真实点击；②滚动前后各一次；③卡片标题/正文/昵称三种点击；④lint+build。本轮已全部执行。

（开发中自发现并修复的问题，值得记住：）
- **筛选 chip 用了 `<span>`**：键盘无法聚焦、读屏不可点。改成 `<button type="button">` 并给 `.chip` 补 `font-family: inherit`。教训：可交互元素语义化优先。
- **mock 数据自相矛盾**：p10 标题写"已标记有帮助"但其回复 `isHelpful:false`，导致它出现在默认流。把 r6 标记为 helpful。教训：种子数据也是测试资产。

## 五、面试可讲的两道题（准备好说法）

**Q：用户端如何兼顾匿名安全与公开答主主页？**
> 身份是"每条内容上的发布模式"而不是"用户的全局属性"。匿名内容对外只有 `{mode:'anonymous'}`，没有任何可反推的稳定标识字段；公开内容才携带昵称和主页入口。公开主页的查询强制限定 identity_mode=PUBLIC，所以主页能建立"答主信誉"，又反查不到该用户的匿名历史。这套规则我从 mock 的 VO 构造层就开始执行，后端任务 3 只是把它换成真实现。

**Q：为什么不做楼中楼和排行榜？**
> 楼中楼会把匿名边界复杂化（回复的作者链可以被逐层反推），而且一级回复 + "楼主标记有帮助"已经能完成"把有效回答顶出来"的目标；排行榜是最强的身份反推器——名次 + 活跃时间能唯一定位到人，和匿名承诺冲突。社区的正反馈应该来自"被标记有帮助"这种内容级认可，而不是流量化的排名。
