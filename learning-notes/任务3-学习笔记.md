> 验收结论：四项全部通过（双账号边界测试、公开响应递归键名扫描零泄露、B 无法修改 A 的任何内容、匿名内容从未出现在公开主页）。后端 62/62 单测 + 30/30 端到端断言 + 浏览器实测。

## 一、05 清单逐条理解 + 代码落点

### 1. 如何从 JWT 取得当前用户

- 链路（任务 2 已建，本轮全量启用）：`JwtAuthFilter` 验签 Cookie 里的 token → 写入 `SecurityContext` → Controller 参数直接写 `@AuthenticationPrincipal LoginUser loginUser`，拿到的 `userId` 只可能来自验过签的 token。
- 例：`post/PostController.create` 用 `loginUser.userId()` 作为 `author_id` 入库；前端传的任何"我是谁"都不看。
- 可空身份：详情页参数声明为 `@AuthenticationPrincipal(required = false)`（游客也能看详情），Service 里对 null 降级为"所有互动标记 false"——身份可选，但一旦有就只信它。

### 2. Service 如何校验"是否为帖子作者"

- 统一入口在 `post/PostService`：`requireVisiblePost(id)`（404 兜底）+ `requireOwned(postId, userId)`（非楼主 403"只有楼主可以执行该操作"）。
- 三种"作者"要分清：**楼主**（帖子的 author，能关评论、标记有帮助）≠ **回复作者**（只能改自己回复的身份）≠ **前端声称的用户**。`ReplyService.setHelpful` 先查回复、再拿父帖 `author_id` 与当前用户比对，两把锁都在 Service。
- 结构性保证：所有越权测试（B 关 A 帖、B 标记 A 帖下的回复）返回的都是 40300，Controller 层根本没有任何"我是楼主"的入参可伪造。

### 3. Entity 为什么不能直接返回给前端

- `PostEntity` 里有 `author_id/school_id/major_id/status/deleted_at`——直接序列化 Entity 等于把匿名体系和筛选内部维度全部裸奔出去，还要靠"记得删字段"来防守。
- 本项目反过来：公开出口只有 `PublicPostVO`，它的原料是 `PostRow`——由 `PostMapper.PUBLIC_COLUMNS` 投影而来，**SELECT 列表里就没有那些列**。想泄露都没有数据可泄露，这是"构造级安全"对比"过滤级安全"的核心优势。

### 4. `PublicPostVO` 和"我的内容 VO"为什么不同

- `PublicPostVO.author` 是 `AuthorView`：匿名时经 `NON_NULL` 序列化后只剩 `{"mode":"anonymous"}`，无昵称/头像/主页链接/稳定标识。
- `MinePostVO` 干脆**没有 author 字段**，带的是 `identityMode`——因为"我的"页永远是本人，前端拿自己的 username/nickname（来自 /api/me）拼展示即可。两个 VO 对应两个视角，而不是一个 VO 里塞可空字段让前端猜。
- 前端再防御一层：`src/api/index.ts` 的 `toAuthor` 只认 `mode==='public' && username` 才展开身份，后端将来多给任何字段也不会显示。
- 公开主页查询额外强制 `identity_mode='PUBLIC'`（`selectRowsByAuthor` 的 `<if test="publicOnly">`），所以"匿名发过什么"无法通过任何人（包括楼主自己的公开主页）反查——只有"我的"页能看到自己的匿名史。

### 5. 学校/专业如何参与 SQL 筛选却不出现在 API JSON

- 只在 WHERE：`<if test="schoolId != null">AND p.school_id = #{schoolId}</if>`。它们从查询参数进来、参与过滤，然后终身消失——投影列没有、VO 字段没有、序列化自然也没有。
- 验收时不是肉眼看 JSON，而是对首页流/详情/公开主页三份响应做**递归键名扫描**（任何层级出现 `authorId/schoolId/majorId/email/userId` 即失败）；`PostControllerTest` 里用 `jsonPath("$..authorId").doesNotExist()` 系列断言固化成了回归测试。
- 附带安全点：`intent` 查询参数绑定的是 Java 枚举，乱填 `?intent=XXX` 会被 `MethodArgumentTypeMismatchException` 处理器收敛成 40000，不会打穿到 SQL。

### 6. `@Transactional` 在哪些场景解决什么问题

- **发帖**（`PostService.create`）：1 行 posts + 最多 3 行 post_tags，两次写。没事务的话标签插入失败会留下"有帖无标签"的半截数据，且筛选会永久漏掉这帖。
- **标记有帮助**（`ReplyService.setHelpful`）：先"清除同帖其他 helpful"再"标当前这条"，两次写。没事务的话中间失败会出现 0 条或 2 条有帮助——"每帖至多一条"是 SQL 部分唯一索引之外的第二道保险，靠事务保证原子。
- **支持/收藏 toggle** 靠联合唯一键 + 吞 `DuplicateKeyException` 处理并发，不需要显式事务（单条写）。
- 判断口诀：**一个业务动作跨多行多表写 → @Transactional；单行幂等写 → 唯一约束兜底。**

### 7. MyBatis-Plus 管基础 CRUD、自定义 SQL 管复杂筛选的原因

- BaseMapper 够用场景：`insert(post)`、`selectById(author_id)` 判归属、`lambdaQuery().exists(...)` 查互动关系——单表、实体全字段。
- 首页流的真实形态是：**投影（不选敏感列）+ 相关子查询计数（回复数/支持数/有无有帮助）+ LEFT JOIN 仅在 PUBLIC 时带出昵称 + EXISTS 半连接筛标签 + 分桶排序**。这些塞进 Wrapper API 既写不出也读不动，所以用 `@Select("<script>...")` 动态 SQL（见 `PostMapper.selectFeed`）。
- 原则：不是"复杂就裸 SQL"，而是"**凡是要控制输出列的查询都必须自定义**"——投影白名单就是匿名体系本身。

## 三、踩坑记录（本轮真实遇到）

| 坑 | 现象 | 根因与解法 |
|---|---|---|
| Java 文本块行尾空格被剥离 | 首页 500，SQL 报 `near 'SELECTp.id'` | `"""SELECT """ + COLUMNS` 中 `SELECT ` 的行尾空格被编译器吃掉，关键字和列名粘死。所有 `@Select` 改成显式字符串拼接 `"SELECT " + COLUMNS + ...`，并在 Mapper 类注释里立此存照 |
| 同上 bug 单测全绿 | 62 个测试 0 失败但服务一启就炸 | 单测 mock 了 Mapper，SQL 从未被执行。**自定义 SQL 必须过真库**：验收脚本里每个查询路径至少打一次真实接口 |
| `@MapperScan("com.patchme.**.mapper")` 漏包 | 启动报 `required a bean of type SchoolMapper` | `**` 只匹配"含点"的多级中间包，dict 的 Mapper 直接放 `com.patchme.dict` 就匹配不到。改成显式列表 `{"com.patchme.**.mapper", "com.patchme.dict"}` |
| MP 3.5.17 `updateById` 重载 | Mockito `verify(never()).updateById(any())` 编译报歧义 | 3.5.17 新增了 `updateById(Collection)` 重载，裸 `any()` 两个都匹配 → 用带类型的 `any(PostEntity.class)` |
| 纯 Mockito 测 Service 报 lambda cache | `MybatisPlus can not find lambda cache for this entity` | `lambdaQuery()` 依赖 MP 的 TableInfo 缓存，真实启动才初始化。测试里 `@BeforeAll` 用 `TableInfoHelper.initTableInfo` 预热（封装为 `support/MpTableInfo`） |
| 切片测 `@AuthenticationPrincipal` NPE | 带登录身份的 MockMvc 请求 500 | `addFilters=false` 绕过了 JwtAuthFilter，SecurityContext 是空的。写 `support/MvcAuth.user(id)` RequestPostProcessor 手工塞入 `LoginUser` |
| `jsonPath(...).value(Map.of(...))` 恒失败 | 响应体明明正确 | Spring 的 Map 相等比较对数字/字符串宽容差异。改为逐字段断言（`author.mode` 值 + `username doesNotExist`） |
| 验收脚本大面积假 FAIL | 明明正确的断言报红 | 两个坑：数字 id 在 JSON 里不带引号，字符串 grep `"12"` 永远匹配不上；ck 条件串里嵌套 `$(curl \| jqv "d['code']")` 的引号在 eval 下走形。统一改为"响应先存变量 → `echo '$VAR' \| python 断言"，**断 JSON 用 JSON 解析，不用文本 grep** |

## 四、面试表述（30 秒版）

> 这个社区产品匿名是命门，所以我把它做成后端数据出口规则而不是前端隐藏。数据库保留 author_id 用于楼主权限和风控，但所有公开接口的响应由白名单投影构造：查询 SQL 的 SELECT 列表里就没有 author_id、学校、专业这些列，匿名内容的作者对象序列化后只剩 `{"mode":"anonymous"}`，不存在可泄露的字段。公开主页查询额外强制 identity_mode 为公开，所以无法反查任何人的匿名历史；身份规则上"匿名承诺不可撤回"——匿名内容永久不能转公开，公开可降级为匿名并即时从主页摘除。楼主操作（关评论、标记有帮助）在 Service 层用 token 身份比对 author_id，越权一律 403。首页"待回答优先、发布早优先"的分桶排序和标签 EXISTS 筛选全在动态 SQL 里完成。这些都有测试兜底：62 个单测里有对响应 JSON 的递归键名泄露扫描，端到端用两个真实账号互踩了 30 条断言。
