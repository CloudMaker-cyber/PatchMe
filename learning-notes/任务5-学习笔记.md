## 一、05 清单逐条理解 + 代码落点

### 1. 举报和处罚为什么分开

- **举报只是线索，处罚只来自人工核实**——这是 02 风控原则第一条。落点上分两个 Service：
  - `moderation/ReportService`：举报入库即 `PENDING`，同目标同人只允许一条未处理单（幂等防刷），此外什么都不动——被举报帖状态、作者账号状态完全不变；
  - `moderation/ModerationAdminService`：管理员逐单核实（CONFIRM/REJECT）或对账号执行处置（WARN/OBSERVE/RESTRICT/BAN/UNBAN），才改变状态。
- 结构性保证：`users.status` 的写路径**只存在于 ModerationAdminService**，而它只挂在 `/api/admin/**` 下。举报计数没有任何代码路径能触到状态机——不是"我们选择不自动处罚"，是"不存在自动处罚的线"。
- 风控自动送审（`RiskDetector` 命中 → `source=SYSTEM` 举报单）同样只是把内容推进队列，systemFlag 不占用户额度、同目标已有待处理单则跳过。

### 2. 限流的时间窗口

- 实现：`moderation/RateLimitService`——不用 Redis，用 MySQL 流水表 `moderation_log` 做计数窗口：`check()` 先查 `COUNT(user_id + action + created_at >= now-窗口)`，达到阈值抛 429（`TOO_MANY_REQUESTS "42900"`）；业务成功后 `record()` 写一笔流水（与写入同事务）。
- 阈值单点表：POST 60 秒 1 条、REPLY 60 秒 5 条、REPORT 10 分钟 10 条、LOGIN_FAILURE 10 分钟 10 次——新增受限动作只改 `GuardedAction` 枚举 + 三个 switch。
- 两道检查的顺序有讲究：**账号状态闸在窗口计数之前**——RESTRICTED/BANNED 直接 403，连"你还剩几条额度"都不回答。
- 登录失败按**小写邮箱**计数（`subject_key` 列）而非 userId：失败时可能根本没有账户，且窗口内密码正确也拒绝（软锁），防撞库枚举。
- 并发下这是软限制（count 和 insert 之间有间隙），首版够用；面试被问"高并发怎么办"可答：换 Redis `INCR + EXPIRE` 或令牌桶，接口的 Service 收口不变、只换实现。

### 3. 管理员 RBAC

- 单层但完整：`SecurityConfig.java:58` `.requestMatchers("/api/admin/**").hasRole("ADMIN")`——角色来自 JWT 验签后的 `LoginUser` authority，不是前端能碰的字段。普通用户带自己的 Cookie 打后台接口得 403；未登录 401。
- `AdminModerationController` 是后台唯一入口，Controller 里没有角色判断——路径前缀被 Security 链罩住，新加后台接口自动继承闸门（加"接缝"不加"防线"）。
- `users.role` 列在库里，注册接口永远写 USER；第一个管理员靠 V2 迁移种子 + `.env` 的 ROOT 密码存在。

### 4. 审计日志

- 每次处置写一行 `moderation_actions`（admin_id、action、target、reason、created_at），后台"审计" tab 查的就是它（`AdminAuditItem` 投影）。
- 与通知联动：处置产生 `MODERATION` 通知（含中文动作文案与理由摘要），举报处理产生 `REPORT` 通知（只回"已确认违规/不予处理"状态）。**两类通知都绝不含举报人/admin 身份字段**——`reporter_id` 压根不在用户侧 VO 里，靠构造防泄露。

### 5. 状态机

- 两条独立状态机，都在枚举注释里写死流转规则：
  - `UserStatus`：NORMAL → WARNED → OBSERVED → RESTRICTED → BANNED，可 UNBAN 回 NORMAL。**只有 RESTRICTED/BANNED `blocksWrite()`**（真正拦发帖/回复/举报），BANNED 额外 `!allowsLogin()`；WARNED/OBSERVED 只影响展示与审核优先级——"渐进式"的含义是每一步都有真实语义，而不是全是封号。
  - `ReportStatus`：PENDING → CONFIRMED / REJECTED，**终态不可再流转**（Service 层闸，重复审核直接 400）。
- 状态机收口验证：`ModerationAdminServiceTest` + 端到端脚本里"RESTRICT 后发帖必 403、UNBAN 后必成功"是回归断言。

### 6. 高风险求助为什么不自动处罚

- `RiskDetector` 输出两类信号，语义完全不同：
  - `atRisk`（自伤/伤人词库）→ 送优先审核 + 读者端显示求助提示。**这是求助不是违规**：自动删帖/封号等于对危机中的用户二次伤害，也可能误伤"从跳楼机上下来"这类文本；误报由人工审核兜底，所以词库召回优先、宁多勿漏。
  - `spam`（手机号/QQ/微信/外链正则）→ 只作为参考标记随举报进队列，同样不自动处置。
- 前端敏感词提示只是体验辅助，服务端检测才是判定——两层都做了，但权限只在服务端。

## 二、本轮开发者提问整理（任务 5 期间，2026-09-27）

1. **"为什么审核后台有个 pending 和待处理两个选项，这俩不是一个意思吗"**——好眼力，是 bug。"待处理"对应不传状态参数（后端默认查 PENDING），我写 chips 数组时多手加了 `{value:'PENDING', label:'PENDING'}`：label 忘翻译，且查询完全重复。修复：删冗余 chip，筛选收敛为待处理/已确认/已驳回（`AdminView.vue:105-112`）。教训：界面上每个可见入口都要真的点一遍，单测测不出"重复入口"。
2. **"先开发到这" / "给我任务 5 的 commit"**——过程性指令，无新问题。

## 三、踩坑记录（本轮真实遇到）

| 坑 | 现象 | 根因与解法 |
|---|---|---|
| 限流窗口整体偏移 8 小时 | 相对时间显示错误、窗口计数不对 | `moderation_log` 的 `DEFAULT CURRENT_TIMESTAMP` 由**数据库服务器时区**决定，JDBC 的 `LocalDateTime` 映射不做换算——两边不同钟窗口静默失效。解法三处同钟：MySQL 容器 `--default-time-zone=+08:00` + 后端容器 `TZ=Asia/Shanghai` + JDBC `connectionTimeZone=Asia/Shanghai`。改完需重建容器并重启后端 |
| 后台出现中英文重复筛选入口 | pending 与待处理并存 | 见上文提问 1；"不传参=默认值"的设计要只在一条路径上存在 |
| 登录失败限流差点漏掉 | 任务卡点名要，首版实现没覆盖 | 补 `LOGIN_FAILURE` 枚举 + `subject_key` 邮箱维度计数。教训：交付前逐条对照任务卡验收项，而不是只对着 02 规范实现 |
| 处置通知泄露举报人风险 | 设计阶段评审发现 | 若 payload 带 reportId 列表或举报来源会反推举报人。收敛：MODERATION 通知只有动作+理由，REPORT 通知只回自己那单的状态 |
| 软锁文案诱导枚举 | 登录限流提示若说"该邮箱失败过多"等于确认邮箱存在 | 统一文案"失败次数过多，请 10 分钟后再试"，且凭据错误不区分"邮箱不存在/密码错" |

## 四、面试表述（30 秒版）

> 风控我采用了渐进式限制而不是按举报次数封号。举报进了队列就只是线索——确认违规、升级限制都以人工核实为准，举报计数没有任何代码路径能改账号状态。账号状态机是提醒、观察、限制、封禁四档，只有后两档真正拦截写入：限流闸在 Service 层，先查账号状态再查时间窗口，用的是 MySQL 流水表 count 近 60 秒/10 分钟的窗口，超限返回 429，登录失败按邮箱维度软锁防撞库。处置和举报处理都写审计日志、都发通知，但通知靠构造不携带举报人和管理员身份。高危内容（自伤关键词）走的是另一条线：只送优先审核加读者求助提示，绝不自动处罚，因为那是求助不是违规。这些有 138 个单测和 59 项端到端断言，包括 RESTRICT 后发帖必 403、UNBAN 后必成功的状态机回归。
